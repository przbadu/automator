# Module 4: Metadata Extraction with Configurable Schemas

## Context

Currently, document chunks in ChromaDB have minimal metadata (`user_id`, `document_id`, `filename`, `chunk_index`). Retrieval is purely vector similarity — no way to filter by topic, type, or other structured attributes.

This module adds:
1. **User-configurable metadata schemas** — users define what fields the LLM should extract (name, type, required, description) via a Settings tab
2. **LLM-powered extraction** during ingestion — extracts structured metadata per the user's schema using dynamic Pydantic models
3. **Metadata-filtered retrieval** — ChromaDB queries can filter on extracted metadata
4. **Frontend UI** — settings tab to manage schema, metadata display on documents

**Scope:** One schema per user (applies to all their documents). Schema changes apply to new uploads only — no re-extraction of existing documents.

**Complexity: ⚠️ Medium** — touches migration, ingestion pipeline, new extraction service, configurable schema CRUD, retrieval filtering, models, frontend display, and tests. Well-scoped and single-pass feasible.

---

## Default Schema Fields (6 fields)

| name | display_label | data_type | required | description |
|------|--------------|-----------|----------|-------------|
| `title` | Title | string | yes | Document title or best descriptive title |
| `summary` | Summary | string | yes | 2-3 sentence summary of the document content |
| `document_type` | Document Type | string | yes | Type: article, report, tutorial, notes, email, legal, technical, other |
| `language` | Language | string | yes | Primary language code (e.g. 'en', 'es', 'fr', 'de') |
| `topics` | Topics | list[string] | no | 3-5 key topics or themes |
| `key_entities` | Key Entities | list[string] | no | Important named entities: people, organizations, products |

## Task 2: Backend Models

**New file:** `backend/app/models/metadata_schema.py`

```python
from pydantic import BaseModel, Field

ALLOWED_DATA_TYPES = ["string", "number", "date", "boolean", "list[string]"]

# Prevent conflicts with ChromaDB built-in metadata keys
RESERVED_FIELD_NAMES = {"user_id", "document_id", "filename", "chunk_index"}

DEFAULT_FIELDS = [
    {"name": "title", "display_label": "Title", "data_type": "string", "required": True, "description": "Document title or best descriptive title"},
    {"name": "summary", "display_label": "Summary", "data_type": "string", "required": True, "description": "2-3 sentence summary of the document content"},
    {"name": "document_type", "display_label": "Document Type", "data_type": "string", "required": True, "description": "Type: article, report, tutorial, notes, email, legal, technical, other"},
    {"name": "language", "display_label": "Language", "data_type": "string", "required": True, "description": "Primary language code (e.g. 'en', 'es', 'fr', 'de')"},
    {"name": "topics", "display_label": "Topics", "data_type": "list[string]", "required": False, "description": "3-5 key topics or themes"},
    {"name": "key_entities", "display_label": "Key Entities", "data_type": "list[string]", "required": False, "description": "Important named entities: people, organizations, products"},
]

class MetadataFieldDefinition(BaseModel):
    name: str = Field(pattern=r"^[a-z][a-z0-9_]*$", max_length=50)
    display_label: str = Field(max_length=100)
    data_type: str  # validated against ALLOWED_DATA_TYPES in router
    required: bool = False
    description: str = Field(max_length=500)

class MetadataSchemaCreate(BaseModel):
    fields: list[MetadataFieldDefinition]

class MetadataSchemaResponse(BaseModel):
    id: str
    user_id: str
    fields: list[MetadataFieldDefinition]
    created_at: str
    updated_at: str
```

**Modify:** `backend/app/models/documents.py` — add `metadata: dict | None = None` to `DocumentResponse`.

## Task 4: Metadata Extraction Service

**New file:** `backend/app/services/metadata_service.py`

Two key functions:

**`get_user_schema_fields(user_id, db)`** — loads user's schema from `metadata_schemas` table, falls back to `DEFAULT_FIELDS`.

**`extract_metadata(text, filename, user_id, db)`** — the extraction pipeline:

1. Load user's schema fields via `get_user_schema_fields()`
2. Build a dynamic Pydantic model via `pydantic.create_model()`:
   - `string` -> `str`, `number` -> `float`, `date` -> `str`, `boolean` -> `bool`, `list[string]` -> `list[str]`
   - Required fields: `(type, Field(description=...))`
   - Optional fields: `(type | None, Field(default=None, description=...))` (or `[]` for lists)
3. Generate JSON Schema from the dynamic model for the LLM prompt
4. Truncate document text to first ~4000 tokens (sufficient for metadata, avoids blowing context)
5. Resolve user's default LLM config (reuse pattern from `backend/app/routers/chat.py:176-191`)
6. Send a single non-streaming LLM call:
   - **System prompt:** "Extract structured metadata from the following document. Respond with valid JSON matching this schema exactly: {json_schema}"
   - **User message:** The truncated document text + filename
7. Parse response into the dynamic Pydantic model
8. Return as dict, or `None` on any failure (best-effort, never blocks ingestion)

**Provider handling:**
- OpenAI-compatible: use `response_format={"type": "json_object"}`
- Anthropic: instruct JSON output in system prompt, parse from response text

**Reuse:** LLM config resolution from `chat.py:176-191`, encryption from `backend/app/services/encryption_service.py`.

**Validation:** Import and call with sample text — returns dict with populated fields matching schema.

## Key Design Decisions

1. **Per-user configurable schema** — stored in `metadata_schemas` table, one row per user. Users define fields via Settings UI. Falls back to 6 default fields when no custom schema exists.
2. **Dynamic Pydantic models** — `pydantic.create_model()` builds models at runtime from user's schema. No LangChain, raw SDK calls only.
3. **Best-effort extraction** — if LLM call fails or no LLM configured, ingestion completes normally without metadata. Never blocks ingestion.
4. **ChromaDB metadata for filtering** — extracted fields flattened into chunk metadata. Lists comma-joined (ChromaDB requires scalar values).
5. **Truncate for extraction** — only first ~4000 tokens sent to LLM. Full document not needed for high-level metadata.
6. **New pipeline status: `extracting_metadata`** — sits between `chunking` and `embedding` in the ingestion flow.
7. **Schema changes = new uploads only** — no re-extraction of existing documents when schema changes. Keeps things simple.
8. **Reserved field names** — `user_id`, `document_id`, `filename`, `chunk_index` blocked to prevent ChromaDB metadata key conflicts.
