# Module 7: Conversation-Aware RAG & Source Citations

⚠️ **Medium** — Touches chat router, retrieval service, message model, SSE protocol, frontend components, and tests. Well-scoped, single-pass feasible.

## Context

Two key usability gaps in the current RAG pipeline:

1. **Retrieval uses only the latest message** — If a user says "tell me more about that" or "what's the pricing?", retrieval searches for those vague phrases instead of understanding conversation context. The fix: use the last few messages to reformulate a context-aware search query via the LLM.

2. **No source visibility** — The LLM is told to cite sources, but users can't see what was retrieved, verify accuracy, or explore source documents. The fix: store retrieved chunks as message metadata and display them as collapsible citations in the UI.

### What This Adds

- **Query contextualization** — LLM reformulates the retrieval query using conversation history
- **Relevance threshold** — Skip RAG injection when retrieved chunks score poorly
- **Stored citations** — Each assistant message records which chunks were used
- **Citations UI** — Collapsible source panel below assistant messages showing document name, chunk preview, and relevance score
- **SSE citation events** — Stream source info to frontend before the response starts

## Task 1: Query Contextualization Service

**New file:** `backend/app/services/query_service.py`

Takes the user's latest message + last N conversation messages and produces an optimized search query.

```python
async def contextualize_query(
    user_message: str,
    chat_history: list[dict],  # last 5 messages
    client=None,
    model: str | None = None,
    provider: str | None = None,
) -> str:
```

**Logic:**
1. If `chat_history` is empty or has only 1 message → return `user_message` as-is (no context needed)
2. Otherwise, call LLM with a system prompt:
   ```
   Given the following conversation history and a follow-up question, reformulate the follow-up
   question into a standalone search query that captures the full intent. Return ONLY the
   reformulated query, nothing else. If the question is already standalone, return it unchanged.
   ```
3. Pass last 5 messages as conversation context + the new user message
4. Use a short `max_tokens=150` — this is a quick reformulation, not a full response
5. On any failure (timeout, error), fall back to returning `user_message` unchanged

**Provider handling:**
- OpenAI-compatible: standard chat completion (non-streaming)
- Anthropic: use `client.messages.create()` (non-streaming)

**Validation:** Call with history `["What is Xyloflux?", "It's a product for..."]` and follow-up `"What's the pricing?"` → returns something like `"What is the pricing for Xyloflux?"`.

## Task 3: Apply Relevance Filtering in Retrieval Service

**File:** `backend/app/services/retrieval_service.py`

After the final result set is computed (whether vector-only, RRF, or reranked), filter out chunks that are below the relevance threshold:

```python
# Filter by relevance threshold
# distance is lower=better (0=identical), threshold is similarity (higher=stricter)
# Convert: similarity_score = 1.0 - distance
threshold = settings.retrieval_relevance_threshold
if threshold > 0:
    results = [r for r in results if (1.0 - r.distance) >= threshold]
```

Also add `relevance_score: float` to `RetrievalResult` dataclass (computed as `1.0 - distance`).

**Validation:** With threshold=0.75, very distant chunks (distance > 0.25) are filtered out. With threshold=0.0, all chunks pass.

## Key Design Decisions

1. **Query contextualization via LLM** — A single non-streaming LLM call reformulates vague follow-ups into standalone queries. Adds ~200-500ms latency but dramatically improves follow-up retrieval. Skipped when there's only 1 message (no history to contextualize).

2. **Relevance threshold** — Configurable via env var. Prevents injecting irrelevant chunks into the system prompt, which can confuse the LLM. Default 0.75 (moderately strict).

3. **Citations stored in message metadata** — Uses the existing `metadata` TEXT column on messages. Stored as JSON `{"sources": [...]}`. Backward-compatible — old messages with empty metadata work fine.

4. **SSE `sources` event** — Sent before streaming starts so the frontend can display "Searching N documents..." while the response generates. Doesn't delay streaming.

5. **Collapsed by default** — Citations panel doesn't clutter the chat. Users who want source verification can expand it.

6. **Preview truncation** — Only first 200 chars of each chunk stored in metadata (not the full chunk). Keeps message storage lean.
