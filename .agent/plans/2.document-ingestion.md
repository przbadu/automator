# Module 2: Document Ingestion & BYO Retrieval

🔴 **Complex** - New backend services, new frontend view, ChromaDB integration, and retrieval wired into chat.

## Architecture

- **SQLite** (aiosqlite) — relational data: documents table (metadata, status tracking)
- **ChromaDB** (local, persistent) — vector storage and similarity search, runs in-process
- **Local filesystem** — uploaded files stored in `uploads/{user_id}/{document_id}/`
- **SSE** — real-time ingestion status updates (consistent with chat streaming pattern)

**Why ChromaDB over sqlite-vec:**
- Purpose-built vector DB with built-in embedding functions, metadata filtering, and similarity search
- Runs fully local and in-process (no separate server needed)
- Persistent storage to disk — survives restarts
- Built-in support for collection-per-user or metadata-based user filtering
- Well-maintained Python library with async support
- No SQLite extension compatibility concerns

**Already done in Module 1 (skipped here):**
- Chat Completions API integration (local LLM)
- Chat history storage (stateless API, we manage memory)

## Task 5: Chunking Service

**File:** `backend/app/services/chunking_service.py`

**Strategy — Recursive character text splitting (no framework):**
1. Read file content as text
2. Split by paragraph (`\n\n`), then sentence (`. `), then word (` `)
3. Accumulate into chunks up to `CHUNK_SIZE` tokens
4. Include `CHUNK_OVERLAP` tokens of overlap between consecutive chunks
5. Use `tiktoken` for token counting

```python
def chunk_text(text: str, chunk_size: int, chunk_overlap: int) -> list[ChunkResult]
```

`ChunkResult`: `content`, `chunk_index`, `token_count`

**Validation:** Call `chunk_text` with known text, verify chunk count, overlap, and token counts are reasonable.

## Task 7: Ingestion Pipeline Service

**File:** `backend/app/services/ingestion_service.py`

Orchestrates the full pipeline as a **background task** (FastAPI `BackgroundTasks`):

1. Update document status → `processing`
2. Read file content from disk
3. Status → `chunking`, run chunking service
4. Status → `embedding`, generate embeddings for all chunks (batched)
5. Store chunks + embeddings in ChromaDB with metadata: `user_id`, `document_id`, `filename`, `chunk_index`
6. Update document status → `completed` with `chunk_count`
7. On error: status → `failed` with `error_message`

**Status broadcasting:** After each status change, push update to per-user SSE queue (see Task 9).

**Startup recovery:** On server start, reset any `processing`/`chunking`/`embedding` statuses back to `pending`.

**Validation:** Upload text file, verify status progression to `completed`. Verify chunks exist in ChromaDB.

## Task 8: Retrieval Service

**File:** `backend/app/services/retrieval_service.py`

**Search flow:**
1. Generate embedding for user's query
2. Query ChromaDB collection with `where={"user_id": user_id}` filter
3. Return top-K results (configurable, default 5)
4. Apply relevance threshold (configurable, default distance cutoff)
5. Return ranked results with document metadata

```python
async def retrieve_relevant_chunks(
    query: str,
    user_id: str,
    top_k: int = 5,
) -> list[RetrievalResult]
```

`RetrievalResult`: `chunk_content`, `document_filename`, `chunk_index`, `distance`

**Validation:** Ingest a document about a specific topic, query for that topic, verify relevant chunks returned with reasonable distances.

## Agent Parallelization Strategy

**Use the Agent tool with `subagent_type: "general-purpose"` and `isolation: "worktree"` to execute independent tasks in parallel within each phase.**

### How to execute each phase

**Phase 1 (Task 1):** Execute directly — single task, no parallelization needed.

**Phase 2 (Tasks 2, 3, 5, 6):** Launch **4 sub-agents in parallel**, each in an isolated worktree:
```
Agent 1 → Task 2 (Schema migration)       — creates backend/migrations/002_documents_schema.sql
Agent 2 → Task 3 (ChromaDB init)          — modifies backend/app/database.py
Agent 3 → Task 5 (Chunking service)       — creates backend/app/services/chunking_service.py
Agent 4 → Task 6 (Embedding service)      — creates backend/app/services/embedding_service.py
```
After all 4 complete, merge each worktree branch into `module-2`. Resolve any conflicts (unlikely — files don't overlap).

**Phase 3 (Tasks 4, 8):** Launch **2 sub-agents in parallel**:
```
Agent 1 → Task 4 (Upload API + storage)   — creates documents router, models, storage service
Agent 2 → Task 8 (Retrieval service)       — creates backend/app/services/retrieval_service.py
```
Merge after both complete.

**Phase 4 (Tasks 7, 9, 10):** Launch **3 sub-agents in parallel**:
```
Agent 1 → Task 7 (Ingestion pipeline)     — creates ingestion_service.py + status_events.py
Agent 2 → Task 9 (Chat integration)       — modifies llm_service.py + chat.py
Agent 3 → Task 10 (Status SSE endpoint)   — adds SSE endpoint to documents router
```
⚠️ **Note:** Tasks 7 and 10 share `status_events.py`. Task 7 should create it; Task 10 should import from it. If run in parallel, one agent creates the module and the other references it — merge carefully.

**Phase 5 (Task 11):** Execute directly — single task, depends on all backend work.

**Phase 6 (Task 12):** Execute directly — single task, full-stack validation.

## Risks and Mitigations

1. **Embedding API availability** — User's local LLM may not support embeddings. Separate `EMBEDDING_BASE_URL` config allows pointing to a different provider (e.g., Ollama with `nomic-embed-text`).
2. **ChromaDB disk usage** — For large document collections, ChromaDB's persistent storage can grow. Not a concern for Module 2 scope (text files only).
3. **Background task reliability** — FastAPI BackgroundTasks run in-process. Startup recovery resets stuck statuses to `pending`.
4. **ChromaDB query performance** — ChromaDB handles up to ~1M vectors efficiently in local mode. Well within scope.
