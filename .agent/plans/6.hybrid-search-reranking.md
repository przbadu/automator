# Module 6: Hybrid Search & Reranking

⚠️ **Medium** - Multiple moving parts but well-scoped; may need iteration on relevance tuning

## Context

Current retrieval (`retrieval_service.py`) is **vector-only** (ChromaDB cosine similarity). This misses exact keyword matches (proper nouns, product codes, acronyms) and has no quality gate — all top-K results are injected regardless of relevance. Adding BM25 keyword search fused with vector search via RRF significantly improves retrieval quality with zero extra latency. An optional cross-encoder reranker (served via API, e.g. Qwen3-Reranker-4B on vLLM) adds precision when configured.

**Defaults:** Hybrid search ON, reranker OFF (enabled by setting `RERANKER_BASE_URL` + `RERANKER_MODEL`).

## Architecture

```
User Query
    │
    ├──► Vector Search (ChromaDB, existing)  ──► top-K candidates
    │
    ├──► BM25 Keyword Search (in-memory index) ──► top-K candidates
    │
    └──► Reciprocal Rank Fusion (merge + dedupe)
              │
              ▼
         Reranker (cross-encoder via API, optional)
              │
              ▼
         Final ranked chunks → RAG system prompt
```

### Task 3: BM25 Keyword Search Service

**New file:** `backend/app/services/keyword_search_service.py`

- `_tokenize(text) -> list[str]` — `re.findall(r'\w+', text.lower())`
- `_build_index(user_id) -> tuple[BM25Okapi, list[dict]]` — fetches all user's chunks from ChromaDB via `collection.get(where={"user_id": user_id})`, tokenizes, builds BM25 index
- `keyword_search(query, user_id, top_k=20, document_type=None) -> list[BM25Result]` — queries cached index, filters zero-score and optional document_type post-hoc
- `invalidate_cache(user_id)` — removes cached index for user
- Cache: `dict[str, tuple[BM25Okapi, list[dict]]]` keyed by user_id, lazy-built on first search

**BM25Result dataclass:** `chunk_id`, `chunk_content`, `document_filename`, `chunk_index`, `bm25_score`, `document_type`

### Task 4: Reciprocal Rank Fusion

**New file:** `backend/app/services/fusion_service.py`

- `reciprocal_rank_fusion(vector_results, keyword_results, k=60) -> list[FusedResult]`
- RRF formula: `score(doc) = sum(1 / (k + rank))` across lists where doc appears
- Deduplicates by `chunk_id`
- Returns sorted by descending RRF score

**FusedResult dataclass:** `chunk_id`, `chunk_content`, `document_filename`, `chunk_index`, `rrf_score`, `document_type`, `vector_rank`, `keyword_rank`

### Task 5: Cross-Encoder Reranker Service

**New file:** `backend/app/services/reranker_service.py`

- `is_reranker_enabled() -> bool` — checks `settings.reranker_base_url` and `settings.reranker_model`
- `rerank(query, documents, top_n) -> list[tuple[int, float]] | None`
  - POST to `{reranker_base_url}/rerank` with `{"model": ..., "query": ..., "documents": [...], "top_n": ...}`
  - Response: `{"results": [{"index": int, "relevance_score": float}]}`
  - Uses `httpx.AsyncClient` (lazy singleton for connection pooling)
  - On any failure: logs warning, returns `None` (graceful fallback to RRF ordering)

This API format is compatible with vLLM, Jina, Cohere, and TEI reranker endpoints.

Refactor into a pipeline while keeping the **same function signature** (`retrieve_relevant_chunks(query, user_id, top_k, document_type) -> list[RetrievalResult]`):

1. **Vector search** (always) — extract existing ChromaDB query into `_vector_search()`, return dicts with `chunk_id` field
2. **If hybrid disabled** — return vector results directly (current behavior)

6. **If reranker fails** — fall through to RRF ordering
7. Return `list[RetrievalResult]` with `distance = 1.0 - score` (preserves lower=better convention)

## Key Design Decisions

1. **`rank-bm25` over SQLite FTS5**: BM25 in Python is simpler, doesn't require schema changes, and works directly with ChromaDB's stored documents. FTS5 would require duplicating chunk text into SQLite.

2. **Cross-encoder reranker via API over `sentence-transformers`**: Avoids ~2GB of PyTorch dependencies. Uses a dedicated reranker endpoint (vLLM, Jina, Cohere, TEI compatible). Off by default — enabled only when `RERANKER_BASE_URL` + `RERANKER_MODEL` are set.

3. **Reranker off by default**: It adds latency. Users opt in when they want higher precision. Hybrid search (BM25 + vector) is on by default since it's fast and always helps.

4. **BM25 cache per user**: Rebuilt from ChromaDB on first search, invalidated on ingestion/deletion. Avoids re-indexing on every query. Simple dict cache is sufficient since this is a single-process app.
